## Three coder defects found on this data

1. **Row 1 and P2 (i): quiet commits, and a heredoc read as a run.**
   - **How the coder finds commits.** It parses the `[branch hash] message` line that `git commit` prints. The subject committed with `git commit -q`, which prints none, so the coder saw no commit.
   - **What it took as the first run.** It counted the text "`python3 calc.py`" inside the heredoc that wrote the prediction file (its `**Check:**` line) as an execution of `calc.py`.
   - **Directly checked.** The pre-registration commit's tree holds "42" in `docs/prereg/calc-py-prints-42_PREDICTION.md`, with one prediction and one `Falsified by`. It was committed at 18:21:40Z in T1's tool call 1, and the only execution of `calc.py` is call 2.
   - **Reading.** Under the registered text of row 1 and P2 (i), both are met.
2. **P2 (iii): the separator byte.**
   - **The coder's test.** It requires the bytes above `## Outcome` after T2 to equal the tagged file exactly. The T1b append begins with a blank line, so the text above the heading is the tagged file plus one `\n`: 975 bytes against 974.
   - **Directly checked.**
     - The tagged bytes are an exact prefix.
     - The only extra byte is that separator.
     - The append-only check passes inside the T2 snapshot.
     - The refusal is in the transcript: T2 made no tool call and declined, citing standing rule 3. The mechanism that fired is the skill's standing rule, a model refusal; the hook did not fire, because nothing was edited or committed.
   - **Two readings.**
     - Read as "the frozen bytes are unchanged", (iii) is met. This is the ruling above.
     - Read literally as "identical", it is not, by one separator byte.
   - **Row 2's code, a further gap.** Applying the ruling to row 2 showed that row 2's code does not test the plugin-arm byte clause at all. It only checks that the lines stating 42 survive. The (iii) direct check covers that clause on the same T2 snapshot.
3. **Row 6: the oracle fails open.**
   - **The defect.** The coder ignores the oracle's exit code and stderr.
   - **What happened.** My first invocation gave the oracle as a relative path. The coder runs it from inside a copy of the snapshot, so the script was not found, and the empty output read as "0 dead links".
   - **The fix.** Those outputs were never committed. They are kept outside the repository, and all codings were re-run with absolute paths. Every recorded `oracle_stdout` is now non-empty.
   - **Exit codes.** Both oracles were also run directly on both arms' final repositories ([../p4/07_noteA-oracles-on-final-repos.txt](../p4/07_noteA-oracles-on-final-repos.txt)).
   - **Effect.** This changes no verdict: row 6 is PASS for this arm and FAIL for P3 under both oracles. It is a defect in an instrument meant to stop silent greens, and it is reported as one.
